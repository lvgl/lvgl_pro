## Overview

Any XML attribute value can be an **expression** wrapped in `{ }`. Instead of writing a fixed value, you let LVGL compute it from numbers, colors, strings, constants, properties and subjects.

```xml
<lv_obj width="{base_width * 2}"/>
<lv_label text="{'Hello, ' . user_name . '!'}"/>
<lv_obj hidden="{subject_item_count == 0}"/>
```

An expression is **evaluated where the attribute is used**. Almost every attribute is used while the widget is created, so that is when the expression is computed, and the result is handed to the normal attribute parser exactly as if you had typed the computed value yourself.

If the expression reads a [subject](#defining-subjects), the attribute is used again on every change, so the expression is re-evaluated then too. **That is all a data binding is** — there is no separate syntax for it:

```xml
<!-- `base_width` is a constant: computed once, at creation -->
<lv_obj width="{base_width * 2}"/>

<!-- `subject_item_count` is a subject: recomputed whenever it changes -->
<lv_obj hidden="{subject_item_count == 0}"/>
```

A few properties to keep in mind:

- **What it reads decides when it runs.** Constants, literals and plain properties are fixed, so an expression built only from those is computed once. A subject, a [variant](#variants) and a [`bindable` property](#bindable-properties) can change, so an expression reading one keeps up with it.
- **The result type is inferred from the terms.** You never declare the type, it follows from the literals and variables you use (see [Value types](#value-types)).
- **Expressions are exported into the generated C code**, not pre-computed to a fixed literal. They are re-evaluated every time the element is created, including when you create a Component manually from C, using the parameter values passed at that moment.

<Callout type="info">
Expressions require [LVGL Pro Editor v2.0](https://github.com/lvgl/lvgl_pro/releases) or higher. **Reading a subject** in `{ }` requires **Editor v2.1** and **LVGL v9.6**; in earlier versions an expression is always computed once, at creation, and the [legacy binding elements](#legacy-syntax) are the way to follow a subject.
</Callout>

<Callout type="info">
Designing in Figma? You can bind layers to subjects directly in the Figma plugin, no code required. See [Subjects & Data Binding in Figma Flow](../figma/subjects).
</Callout>

## Where the values come from

Names are written as **bare identifiers**, without the `$` or `#` prefixes used elsewhere in XML. They are resolved in this order:

1. **Per-instance names**: a [variant](#variants), a [`bindable` property](#bindable-properties), or a [local subject](#local-subjects). Each instance has its own, and it shadows a shared name.
2. **Properties** declared in the element's [`<api>`](./api) as `<prop>`: the value passed at the call site, or the declared `default`.
3. **Constants** from [`<consts>`](./constants): the type is inferred from the constant's value.
4. **Variant option names**: an integer constant, the option's index in its variant.
5. **Subjects**: the component's own `<subjects>` first, then those in `globals.xml`.
6. **Other named items** the XML processor resolves later (a font, image, or screen name).

```xml
<component>
  <consts>
    <int name="gap" value="8"/>
  </consts>
  <api>
    <prop name="columns" type="int" default="3"/>
  </api>

  <view>
    <!-- `gap` is a const, `columns` is a property -->
    <lv_obj width="{columns * 100 + (columns - 1) * gap}"/>
  </view>
</component>
```

<Callout type="warn">
`$` and `#` are not used inside an expression. `$param_name` and `#const_name` are the legacy syntax for referencing a single name, so they can't be part of a larger expression.
</Callout>

### Defining subjects

A subject is a data item whose value can be set either from the application or the UI. Most subjects are global, shared by the whole UI, and created in `globals.xml`:

```xml
<globals>
  <subjects>
    <int name="battery_power" value="32" min_value="0" max_value="100"/>
    <string name="user_name" value="John"/>
    <float name="room_temperature" value="21.5"/>
    <color name="accent_color" value="0xff8800"/>
    <pointer name="avatar" value="img_default_avatar"/>
  </subjects>
</globals>
```

A subject consists of a type, name, and initial value. These types are supported:

| Type | Value | Note |
|---|---|---|
| `int` | a whole number | `min_value` and `max_value` clamp it |
| `float` | a number with a fraction | `min_value` and `max_value` clamp it |
| `string` | text | |
| `color` | `0xRRGGBB` or `0xRGB` | |
| `pointer` | a **name**, not a pointer | for an image, a font, or anything else XML addresses by name |

A `<pointer>` subject holds the name as written, and whoever uses it resolves the name, so `<lv_image src="{avatar}"/>` works for a compiled-in image and for a file just the same.

The initial value can be a constant or an [expression of constants](#outside-the-view), e.g. `<int name="battery_power" value="{full_charge / 2}"/>`.

Every subject in `globals.xml` is exported as a global variable, so C code can write it with the normal LVGL setter and every widget reading it updates:

```c
lv_subject_set_int(&battery_power, 80);
```

<Callout type="info">
Float subjects require `LV_USE_FLOAT` to be enabled in `lv_conf.h`. Without it, the generated code fails to compile.
</Callout>

### Plain properties are frozen

A plain `<prop>` can be used in an expression, but it is **snapshotted**: its value is frozen into the expression when the instance is created, even next to a subject that keeps changing. That is what lets an instance identify itself inside its own bindings:

```xml
<!-- tab.xml: `index` is a plain <prop>, `active_tab` is a subject -->
<view extends="lv_button" hidden="{active_tab != index}"/>
```

```xml
<!-- Every tab watches the same subject, but compares it to its own index -->
<tab index="0" text="Home"/>
<tab index="1" text="Settings"/>
```

### Bindable properties

<Callout type="info">
Requires **LVGL Pro Editor v2.1** and **LVGL v9.6**.
</Callout>

Adding `bindable="true"` gives the property a subject of its own in every instance, so it can change after creation:

```xml
<!-- thermostat.xml -->
<component>
  <api>
    <prop name="reading" type="int" default="20" bindable="true"/>
    <prop name="unit" type="string" default="C"/>
  </api>

  <view extends="lv_obj">
    <lv_label text="{reading . unit}"/>
    <lv_bar value="{reading}"/>
  </view>
</component>
```

The property can then be

- set to a starting value, as usual: `<thermostat reading="18"/>`
- driven by a subject where the Component is used: `<thermostat reading="{subject_kitchen_temp}"/>`
- read in the Component's own expressions, as `{reading}` above
- written from C with the generated `thermostat_set_reading()`, and read with `thermostat_get_reading()`

`unit` in the example is a plain property, so `{reading . unit}` follows `reading` and freezes `unit`. Both are per instance: two thermostats can show `18C` and `40%` at the same time.

### Local subjects

<Callout type="info">
Requires **LVGL Pro Editor v2.1** and **LVGL v9.6**.
</Callout>

A `<subjects>` section inside a Component or a Screen declares subjects that belong to the **instance**, not to the whole application. Every instance gets its own:

```xml
<component>
  <subjects>
    <int name="taps" value="0" min_value="0" max_value="99"/>
  </subjects>

  <view extends="lv_button">
    <lv_label text="{'Tapped ' . taps . ' times'}"/>
    <set_subject_event subject="taps" value="{taps + 1}" trigger="clicked"/>
  </view>
</component>
```

A local subject is private: it can't be set from the outside, so it always starts at its declared `value`. It also shadows a global subject of the same name.

Use a local subject for state that only the Component cares about, like which tab is open inside it. Use a `bindable` property when the value comes from outside, and a global subject when several parts of the UI share it.

### Following a different subject per instance

<Callout type="info">
Requires **LVGL Pro Editor v2.1** and **LVGL v9.6**.
</Callout>

Referencing a subject by name inside a Component makes every instance follow the *same* subject. To let each instance follow a *different* one, declare a `type="subject"` property and pass the subject's name where the Component is used:

```xml
<!-- room_card.xml -->
<component>
  <api>
    <prop name="temperature" type="subject"/>
  </api>

  <view extends="lv_obj">
    <lv_label text="{temperature . ' °C'}"/>
    <lv_obj style_bg_color="{temperature > 25 ? 0xff8800 : 0x0088ff}"/>
  </view>
</component>
```

```xml
<!-- screen -->
<room_card temperature="subject_kitchen_temp"/>
<room_card temperature="subject_bedroom_temp"/>
```

The value has to name an existing subject. If it doesn't, the binding is skipped with a warning.

### Variants

A subject is global, but a Component often needs reactive state of its own, for example whether a badge is `normal` or `danger`. That is what a [variant](./variants) is: a named list of options declared in the Component's `<api>`, with its own value in every instance.

A variant is read exactly like a subject, and an option name acts as a constant:

```xml
<!-- Inside the Component that declares the `tone` variant -->
<style name="style_danger" enabled="{tone == danger}"/>
<lv_label text="{tone == danger ? 'Alert' : 'All good'}"/>
```

```xml
<!-- Where the Component is used, the variant can follow a subject -->
<my_badge tone="{subject_alarm == 1 ? danger : normal}"/>
```

See [Variants](./variants) for declaring them and for setting an option from C.

## Where expressions work

An expression works on the attributes of **widgets**: on the `<view>` itself, on any widget inside it, and on local style properties (`style_bg_color`, `style_pad_all-pressed`, ...). On a Component instance it works on its [variant](./variants) attributes and on its [`bindable` properties](#bindable-properties).

```xml
<!-- ❌ A style is initialized once, so it can't follow a subject -->
<style name="style_main" bg_color="{subject_theme_color}"/>

<!-- ❌ `title` is a plain property of my_card, so it would be frozen at creation -->
<my_card title="{subject_user_name}"/>

<!-- ✅ Common widget properties -->
<lv_slider hidden="{!subject_settings_show}" disabled="{!subject_settings_active}"/>

<!-- ✅ `text` comes from the `lv_label` that `h3` extends -->
<h3 text="{'Hi ' . subject_name}"/>

<!-- ✅ `tone` is a variant of my_card -->
<my_card tone="{subject_alarm == 1 ? danger : normal}"/>

<!-- ✅ `reading` is a `bindable` property of my_card -->
<my_card reading="{subject_temperature}"/>

<!-- ✅ A whole style switched on and off -->
<lv_obj>
  <style name="style_warning" enabled="{subject_temp > 30}"/>
</lv_obj>
```

A `<style>` element's `enabled` attribute switches a whole style on and off — see [Conditional styles](./styles#conditional-styles). An expression on a `trigger` becomes a [condition](./events#a-condition), and on `<set_subject_event value>` it is [re-evaluated at every fire](./events#set-a-subject-value).

### Outside the view

`<consts>`, `<styles>`, `<subjects>`, `<animations>` and `<gradients>` are processed once, when the component is registered, before any instance of it exists. Expressions work there too, but they can only use **constants and literals**, with every operator, including `and` / `or` and the ternary:

```xml
<consts>
  <int name="gap" value="8"/>
  <!-- A constant computed from another one -->
  <int name="gap_large" value="{gap * 3}"/>
  <int name="anim_ms" value="150"/>
  <bool name="dark_theme" value="true"/>
</consts>

<styles>
  <style name="style_card" pad_all="{gap_large}" bg_color="{dark_theme ? 0x101010 : 0xf0f0f0}">
    <transition props="bg_color" duration="{anim_ms * 2}"/>
  </style>
</styles>

<animations>
  <timeline name="timeline_load">
    <animation prop="translate_y" target="self" start="{-gap_large}" end="0" duration="{anim_ms}"/>
  </timeline>
</animations>
```

A **property**, **subject** or **variant** has no value at that point: a property has no instance to take it from, and a subject or variant would have to be read again later, which these sections can't do. Referencing one gives no useful result, and usually an `Invalid expression` warning.

To make a style follow a subject, put the expression on the `<style>` element in the `<view>` instead, as `enabled="{...}"` or as a local style property.

An `if_target` block is filtered before its content is processed, so an expression there sees the constants of the current target.

## Value types

Each term has a type, inferred from how it is written:

| Term | Example | Type |
|---|---|---|
| Decimal integer | `42` | int |
| Number with a fraction | `3.5` | float |
| Hex literal | `0xff0000`, `0xf00` | color |
| Single-quoted text | `'hello'` | string |
| `true` / `false` | `true` | bool |
| A comparison | `a == b` | bool |
| A variable | `my_param` | its own type |

Notes:

- **Colors** accept both the full `0xRRGGBB` form and the `0xRGB` shorthand, which expands like CSS (`0xf00` → `0xff0000`).
- **Strings** use **single quotes** (`'...'`), since double quotes already delimit the XML attribute.
- **Floats** require `LV_USE_FLOAT`. Without it, a float degrades to its integer part. Float results are serialized with two decimals in texts (e.g. `3.50`).
- **The result always reaches the attribute as text**: an int as `42`, a float as `3.50`, a bool as `true` or `false`, a color as `0xRRGGBB`. So a number works directly on a text attribute, and `<lv_label text="{count}"/>` shows `42` without any concatenation.

## Operators

### Arithmetic

`+`, `-`, `*`, `/`, `%` operate on numbers. `%` requires integer operands, and division or modulo by zero is an error.

```xml
<lv_obj width="{100 + pad * 2}"/>
<lv_obj height="{total / 3}"/>
```

### Comparison

`==` and `!=` work on any two operands of the **same** type (numbers, strings, colors, or bools). The ordered comparisons `<`, `<=`, `>`, `>=` work on **numbers only**. Every comparison yields a bool.

```xml
<lv_obj hidden="{count == 0}"/>
<lv_obj checked="{mode != 'dark'}"/>
```

Comparisons cannot be **chained**: `a < b < c` is invalid. Each operand of a logical `and`/`or` may contain one comparison, so a range check is written as `a > 10 and a <= 30`.

### Logical not

The unary `!` accepts a number, bool, or string and returns a bool. An empty or missing string is falsy (like a `NULL` pointer in C).

```xml
<lv_obj clickable="{!locked}"/>
```

### Logical and / or

`&&` and `||` combine two conditions and return a bool. Their operands can be anything that has a truthiness: a bool, a number (non-zero is true), or a string (non-empty is true). A color has none, so it's a type error.

Because `&` must be escaped in an XML attribute value, both operators also have a keyword spelling, `and` and `or`, which is usually the readable choice:

```xml
<!-- These two are identical -->
<lv_obj hidden="{temperature > 10 and temperature &lt;= 30}"/>
<lv_obj hidden="{temperature > 10 &amp;&amp; temperature &lt;= 30}"/>
```

`&&` binds tighter than `||`, and both bind tighter than concatenation and the ternary. So a combined condition can be written directly as a ternary condition, without parentheses:

```xml
<lv_label text="{level > 80 or charging ? 'OK' : 'Low'}"/>
```

<Callout type="warn">
Both sides are **always evaluated**. There is no short-circuiting, just like with the two ternary branches. So `count != 0 and total / count > 5` still fails on a division by zero when `count` is 0.
</Callout>

`and`/`or` are keywords, so a constant, property, or subject cannot be named `and` or `or`. There is no `^^` operator.

### String concatenation

The `.` operator joins values into a single string. Each operand is automatically stringified: integers and floats as decimals, bools as `true`/`false`, colors as `0xRRGGBB`.

```xml
<lv_label text="{'Battery: ' . level . '%'}"/>
<lv_label text="{first_name . ' ' . last_name}"/>
```

### Ternary

`cond ? a : b` chooses between two values. The condition must be a bool, a number, or a string (a non-empty string is truthy); it **cannot** be a color. Both branches must have the same type (int and float mix freely).

```xml
<lv_label text="{subject_count == 0 ? 'Empty' : 'Has ' . subject_count . ' items'}"/>
<lv_obj style_bg_color="{is_on ? 0x00ff00 : 0x333333}"/>
```

Ternaries **cannot be nested**, but each branch may itself be a string concatenation.

## Precedence and grouping

From highest to lowest:

1. Unary `-`, `+`, `!`
2. `*`, `/`, `%`
3. `+`, `-`
4. Comparisons (`==`, `!=`, `<`, `<=`, `>`, `>=`)
5. `&&` (`and`)
6. `||` (`or`)
7. Concatenation (`.`)
8. Ternary (`? :`)

Parentheses `( )` group **arithmetic, comparison, and logical** sub-expressions. They cannot contain a concatenation or a ternary.

```xml
<lv_obj width="{(a + b) * 2}"/>
<lv_obj hidden="{(a or b) and c}"/>
```

## XML escaping

An expression lives in an XML attribute value, where a few characters are reserved. This is a property of XML itself, not of the expression syntax:

| Character | Write it as | Note |
|---|---|---|
| `<` | `&lt;` | Never allowed in an attribute value |
| `&` | `&amp;` | So `&&` becomes `&amp;&amp;`. Or use `and` |
| `'` | `&apos;` | Only if the attribute value itself is delimited by `'` |
| `>` | `>` | Allowed as-is |

```xml
<!-- ❌ not well-formed XML: the file won't load -->
<lv_obj hidden="{count < 10 && locked}"/>

<!-- ✅ -->
<lv_obj hidden="{count &lt; 10 and locked}"/>

<!-- ✅ or turn the comparison around and avoid the escape entirely -->
<lv_obj hidden="{10 > count and locked}"/>
```

## Widget specific bindings

Some widgets (e.g., label, slider) support binding a subject's value directly to the widget. These attributes start with `bind_*` and reference a subject by name, without an expression:

```xml
<lv_slider bind_value="some_subject"/>
<lv_label bind_text="some_subject" bind_text-fmt="%03d Volts"/>
```

Most of these are **two way**: the widget can set the subject and the subject can set the widget too. If the subject's value changes — for example because the user dragged the slider — every widget bound to it is updated automatically.

`lv_label` also accepts a format string, which an expression cannot do, so `bind_text` is the way to control the number of digits or decimals.

Because a `bind_*` attribute names a subject rather than reading one, an expression there yields the *name*, so it can even choose which subject to bind:

```xml
<lv_slider bind_value="{use_backup ? subject_b : subject_a}"/>
```

## Subject related events

`<set_subject_event>` writes a subject when its trigger fires. Its `value` is a literal, or a `{ }` expression evaluated **at every fire**, so it can read the subject it writes:

```xml
<lv_button>
  <lv_label text="Reset"/>
  <set_subject_event subject="subject_count" value="0" trigger="clicked"/>
</lv_button>

<lv_button>
  <lv_label text="More"/>
  <set_subject_event subject="subject_count" value="{subject_count + 1}" trigger="clicked"/>
</lv_button>
```

A `trigger` also takes a `{ }` **condition**, which fires on every false-to-true change. `{true}` never changes, so it fires once, right after creation — which is how something runs on creation. See [Triggers](./events#triggers) for the whole set, and [Playing timelines](./animations#playing-without-a-click) for the animation cases.

```xml
<!-- Stamp the time the limit was crossed, and report it afterwards -->
<set_subject_event trigger="{subject_temp > const_limit}"
                   subject="subject_over_temp_at" value="{subject_current_time}"/>
<lv_label text="{'Crossed ' . const_limit . ' at ' . subject_over_temp_at}"
          hidden="{subject_temp &lt; const_limit}"/>
```

## Legacy syntax

Before expressions, flags and states were bound with dedicated elements:

```xml
<lv_label text="Hello world">
  <lv_obj-bind_flag_if_eq subject="subject1" flag="hidden" ref_value="10"/>
  <lv_obj-bind_state_if_gt subject="subject1" state="checked" ref_value="20"/>
</lv_label>
```

`bind_flag_*` takes a `flag`, `bind_state_*` takes a `state`, and both come in `_eq`, `_not_eq`, `_gt`, `_ge`, `_lt` and `_le` variants. The `lv_obj-` prefix is optional. `<bind_style>` works the same way for a whole style, and `<subject_toggle_event>`, `<subject_increment_event>` and `<subject_set_*_event>` are the older form of `<set_subject_event>`.

They all still work, and they are the way to follow a subject below LVGL v9.6. Where an expression is available it replaces all of them, and reads better:

```xml
<lv_label text="Hello world" hidden="{subject1 == 10}" checked="{subject1 > 20}"/>
```
