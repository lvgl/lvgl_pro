---
title: Variants
description: Declare a Component's visual variations, like size or tone, and switch between them at runtime.
---

Most Components exist in a few flavors: a button that is `small` or `large`, a badge that is `normal` or `danger`. A **variant** declares such a dimension once, and every instance can pick an option from it — statically, from a subject, or from C at runtime.

```xml
<my_badge size="large" tone="danger"/>
```

## Overview

A variant is a named list of options, declared in the Component's [`<api>`](./api):

```xml
<component>
  <api>
    <variants>
      <variant name="size" options="small large" default="small"/>
      <variant name="tone" options="normal danger" default="normal"/>
    </variants>
  </api>
  ...
</component>
```

- `name` - The name of the variant. It becomes a property of the Component.
- `options` - Space separated list of the option names.
- `default` - The option to use when the instance doesn't set one. If it's missing or unknown, the first option is used.

Each variant is **per-instance reactive state**: ten instances of the same Component can be in ten different states, and switching one of them updates only that instance. This makes variants the Component-level counterpart of [subjects](./data-binding), which are global.

<Callout type="info">
Variants are useful when a Component's *appearance* has a fixed set of named states. For free-form data (a temperature, a user name) use a subject or an [`<api>`](./api) property instead.
</Callout>

## Reacting to a variant

A variant is meaningless until something reads it. There are two ways, and they are usually combined.

### Switching styles

`<bind_style>` attaches a style while a variant has a given option. Use the variant's name as `subject` and an option name as `ref_value`:

```xml
<component>
  <api>
    <variants>
      <variant name="size" options="small large" default="small"/>
      <variant name="tone" options="normal danger" default="normal"/>
    </variants>
  </api>

  <styles>
    <style name="style_normal" bg_color="0x0000ff"/>
    <style name="style_danger" bg_color="0xff0000"/>
    <style name="style_small" height="40"/>
    <style name="style_large" height="100"/>
  </styles>

  <view extends="lv_button">
    <style name="style_normal"/>
    <bind_style name="style_danger" subject="tone" ref_value="danger"/>
    <bind_style name="style_small" subject="size" ref_value="small"/>
    <bind_style name="style_large" subject="size" ref_value="large"/>

    <lv_label name="title" text="Title"/>
  </view>
</component>
```

This is the recommended way to express the *visual* difference between options: the styles stay declarative, and only the option selection changes at runtime.

### In expressions

A variant can also be used in [`@{ }` bindings](./data-binding#expression-binding), where:

- a **variant name** reads the currently selected option,
- an **option name** is a constant that can be compared against it.

```xml
<!-- Show the subtitle only in the large size -->
<lv_label name="subtitle" text="Subtitle" hidden="@{size == small}"/>

<!-- A variant and a global subject in one expression -->
<lv_label text="@{mode == on ? 'n=' . subject_count : 'off'}"/>
```

Because `@{ }` re-evaluates on every change, switching the variant updates these attributes immediately. In a plain [`{ }` expression](./evaluate) a variant works too, but it's read only once, when the element is created.

## Selecting an option

### On the instance

A variant behaves like a normal property where the Component is used:

```xml
<my_badge size="large" tone="danger"/>
```

An unknown option name falls back to the variant's `default` and logs a warning.

The value can also be a [binding](./data-binding#expression-binding), so a variant can follow a subject:

```xml
<my_badge tone="@{subject_level > 100 ? danger : normal}"/>
```

Note that such a binding is evaluated in the **surrounding** element's scope: `subject_level` needs to be visible there, while `danger` and `normal` need to be options of `my_badge`'s `tone` variant.

### From C

```c
lv_xml_set_variant(badge, "size", "large");
```

The variant is searched on the given widget and then up along its parents, so passing any widget inside a Component instance works too. Every `bind_style` and `@{ }` expression referencing the variant updates immediately.

## Name resolution

Inside expressions a bare identifier is resolved in this order:

1. **variant name**
2. `<api>` property
3. constant
4. variant option name
5. subject
6. anything else is kept as a plain string (a font or image name, for example)

Two consequences worth remembering:

- A variant **shadows** a property, constant, or subject of the same name. Avoid such collisions.
- **Option names have to be unique across a Component's variants**, otherwise a bare option name in an expression is ambiguous — the first declared variant wins, and registration logs a warning. `<bind_style>` is exempt, since its `subject` attribute already tells which variant the `ref_value` belongs to.

<Callout type="warn">
The order of `options` defines the integer value of each option in the exported C code. Reordering them is a breaking change for code that was already generated; adding new options at the end is safe.
</Callout>
